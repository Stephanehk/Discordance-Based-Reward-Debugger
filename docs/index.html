Discordant-Based Reward Debugger

A tool for debugging reward functions.

You give it a reward function implemented in Python and your environment's source code. It constructs comparisons where it hypothesizes your preferences will most likely differ from the ranking induced by the reward function. In light of those hypotheses, you update your reward function as you see fit.

In popular RL environments such as Meta-World, it uncovers previously documented and novel reward misspecifications. In ExploitGym, it uncovers a reward misspecification that was later exploited in practice, when a collective of AI agents attacked OpenAI and Hugging Face infrastructure while being evaluated on similar tasks.

Set up ↓ GitHub Full README
Built on Claude Code. The whole workflow is a set of slash commands you run inside Claude Code. We developed and tested it with a Claude Max subscription running Claude Opus 4.8, and that is the setup we recommend.

What you need

  • Claude Code. Every command below is run from the repo's root directory.
  • Python 3.10+ with numpy and gymnasium.
  • A Gym/Gymnasium environment that contains your environment source code. It can be installable (gym.make("Hopper-v4")) or your own Python implementation.
  • A reward function, or just an idea of one. Either an implementation for your environment, or a description in natural language when the tool asks for it.

Set up

  1. Install Claude Code and pick the model

    Install Claude Code, then select Opus 4.8 with /model. The quality of the comparisons depends on the model doing the reasoning.

  2. Clone and install

    git clone https://github.com/Stephanehk/Discordant-Based-Reward-Debugger.git
cd Discordant-Based-Reward-Debugger
pip install -r requirements.txt

  3. Describe your environment

    The only thing the tool needs from you to begin is a description of your environment, written as a single file: workspaces/<name>/env_config.py. Everything else is derived from it. The file exposes four things:

    NameWhat it is
    make_env()returns a Gym/Gymnasium-compatible env; wraps gym.make(...) or your own class
    OBS_DESCRIPTIONplain-English description of what every observation dimension means
    ACTION_DESCRIPTIONplain-English description of the action space
    MAX_EPISODE_STEPSthe episode horizon

    You don't have to write it by hand. Point Claude Code at your environment's source and ask it to generate the file. Worked examples are in the repo under workspaces/ — pandemic, merge, metaworld_drawer_open, and others.

    A prompt that works well 
    I'm setting up the Discordant-Based Reward Debugger on a new environment. Read my environment's source code (below / at <path>) and write workspaces/<name>/env_config.py conforming to the tool's contract:

- make_env() returning a Gym/Gymnasium-compatible env. If the env can render RGB frames, make make_env accept a render_mode kwarg and set CAPTURE_FRAMES = True at module level so rollouts record a video per episode.
- OBS_DESCRIPTION: str describing what each observation dimension means, in plain English.
- ACTION_DESCRIPTION: str describing the action space.
- MAX_EPISODE_STEPS: int (the horizon).

Also write the companion workspaces/<name>/viz.py (see below for how I want trajectories visualized). Follow the contracts in CLAUDE.md exactly, and model both files on the committed examples in workspaces/merge/ (video) and workspaces/pandemic/ (plots).

My environment: <paste the source, or give the import path / gym id>

  4. Decide how your trajectories should be visualized

    You have three choices, set up alongside env_config.py:

    1. A video of the real environment — best when your env has a renderer. Set CAPTURE_FRAMES = True in env_config.py; rollouts record one frame per step into an mp4.
    2. Rendered plots or images — best for observation-rich envs with no natural picture. A small viz.py draws the trajectory itself.
    3. Text only — omit viz.py, and each comparison still shows a plain-English list of how the two runs differ.

  5. Run it

    Open Claude Code in the repo's root directory and run:

    /repair-setup <env_name>

    <env_name> is any short name you pick for this piece of work. That command prints one thing to your terminal: a link to http://127.0.0.1:8000. Open it.

    From then on, everything happens on that page — Claude posts its explanations, code, videos, and questions there, and you answer there. Each step ends with a Continue button.

    Some steps can take a while — up to an hour or longer. The speed of the tool depends on the speed of your environment, because it rolls out policies in that environment. Check in on its progress while you do something else.

What you get back

Once enough behavior has been collected, the page fills with comparisons.

Pairs
Two videos: on the left, the run your reward function preferred; on the right, the alternative. Underneath, a one-line "why they disagree" and how the preferred run differed.
Lotteries
A gamble: would you rather have this certain run C, or a probability distribution between run A and run B?

Below the comparisons, the page asks you to pick one:

Edit the reward function
Change the code yourself, or tell Claude in plain language what to change.
Add another characteristic
Name something you need in order to judge the comparisons; it gets measured and folded in.
View more comparisons
Surface more pairs and lotteries from the behavior already collected.
Finish and submit
Locks the current reward in as your final answer. Not reversible.
